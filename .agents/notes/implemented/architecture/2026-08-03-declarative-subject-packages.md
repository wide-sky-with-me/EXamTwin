# Agent Note: 科目以声明式 SubjectPack 加宿主 provider 注册表扩展

Status: implemented

## Problem

新增科目要求修改主流程：通用模块直接判断 `subject_code == "9660"`、固定导入数学与经济工具、在缺少
上下文时静默回退到数学，知识点还维护在逐科 seed 常量文件中。继续增加科目会放大跨科静默写入和分支
蔓延。

## Decision

- 科目差异只存在于 `subject-packs/<id>/`：`manifest.json` 声明科目代码、Unit 映射、课纲解析、配对规则、
  完整性阈值与工具 allowlist；`SKILL.md` 只保存已审核的作答语义。包不能导入或执行任意代码。
- 需要专用实现时，宿主在 `SubjectProviderRegistry` 注册 Board、课纲 normalizer、视觉政策或答题能力，
  包只按 ID 引用；加载器失败关闭地校验 schema、越界、唯一性、正则与工具子集。
- 所有领域写入要求显式 `SubjectContext`，缺失即失败，不存在默认科目。
- 知识点不入包：课程结构由通用 `CurriculumExtractor` 从真实课纲生成候选。
- `scripts/check_architecture.py` 拒绝通用模块出现已安装科目代码字面量；合成科目 `9999` 测试证明已有
  通用能力的新科目只需添加包。

## Alternatives considered

- **任意可执行插件（包内 Python）** — 灵活度最高，新科目可自带任何规则。但配置文件会成为不受控的代码
  执行面，信息安全与审计都无法保证。
- **逐科 seed 常量与主流程分支** — 接入最快，前两科就是这样起步。但每加一科都要改通用模块，且知识点
  常量与真实课纲脱节，无法用漂移门禁验证。
- **封闭的学科工具 Literal 枚举** — 类型最严格。但每加一个学科能力都要改共享契约和前端；改为可扩展的
  能力 ID 加运行时注册校验，持久化与前端只依赖少量稳定产物形状。

## Consequences

- **收益**：普通新科目只加包；专用能力只加受审查 provider；跨科静默写入在边界失败。
- **代价与已知上限**：每个新专用能力仍需宿主代码改动与评审；包 schema 变化需要版本迁移。合成第三科只
  证明接缝成立，不等于真实第三科已接入。
