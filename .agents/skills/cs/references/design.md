# Design：为明确改变做实现设计

把“要做什么”收成“实现该怎么安排”；有 issue 时写回，无则对话交付。不写代码、不建 issue。

全局规则（开工协议、管理强度、质量、实现经济性、UI、完成≠关闭）见 `SKILL.md` 与 [quality](quality.md)、[economy](economy.md)、[ui-spec](ui-spec.md)。本文件只写 Design 增量。

## 阅读入口

- [原则](#原则) → 先现状说明再设计
- [行动指南](#行动指南) → 锁定目标、现状、质量、方案
- [产物契约](#产物契约) → 有/无 issue 的交付形状

## 背景

目标明确不等于实现判断成立。未先讲清触发如何产生结果就谈归属与接口，实现容易漂移。Design 先贴着代码建立现状与影响，再形成可执行的实现安排。

## 原则

**先查 `codestable/`，再贴代码。** project / epic spec、notes、历史 issue 里有代码读不出的取舍与解法。**Design 在形成方案前必须完成 `SKILL.md` 开工协议中的检索**（本会话同主题已扫过且无新写入除外）。

**设计必须贴着代码。** 在 `codestable/` 上下文之上确认现有能力、分工、命名、数据流、状态、错误、配置、依赖与测试面。

**先现状说明，再设计未来。** 默认做跨模式**现状说明**（见 [explore](explore.md)）。解释不清、跨多边界或值得复用时，升级为 Explore issue，不在此硬推方案。

**根因指向状态边界时，先外推再定方案。** Bug 的根因不是天然只属于当前调用点。若现状或根因涉及共享可变状态、锁、回调/反向依赖、异步任务、外部 I/O，或“检查状态 → 锁外工作 → 提交状态”的路径，必须把它当作架构风险信号：找出该状态的唯一所有者、同一状态域的相邻入口、允许的转换与互斥条件，以及可能重入或写回旧快照的边界。先判断它确实是孤立缺陷，还是共享责任边界已经错误；后者要重新设计责任与转换协议，不能只在当前症状旁补分支。这个外推只在有触发信号时进行，不把每次 Design 变成全仓并发审计。

**写设计，不写实现。** 回答分工、数据/请求路径、边界、顺序、验证、风险与未知；不写伪代码长篇，不提前实现，不为“设计感”造抽象。

**像教新同事。** 自然语言讲清分成几部分、各负责什么、东西怎么流、哪些边界不碰；模块名只作落点。

**归属仍对则扩展做深；业务形状已变则先重切再改行为。** 扩展不是默认正确。方案走最小充分梯子——最小充分看系统总复杂度，不看「少动几个文件」。细节见 [economy](economy.md)、[code-design](code-design.md)。

**Design 要做腐化判断，分清两种场景。** 一是**本次变化造成失配**：新状态域、规则或生命周期已不属于旧容器，必须先重切归属，再加新行为。二是**历史积累已经腐化**：本次入口附近的代码早已职责混杂、重复投影、跨域状态耦合或名字无法说明归属。不能因为它不是本次新增而在其上继续补分支；若清理是理解、正确修改或验证本次目标的前提，应把清理作为本次 Design 的结构步骤并保持外部行为。若腐化真实但超过本次边界，则显式记录为后续 refactor / issue，不能沉默绕开或伪装成已解决。
**UI 规格不是组件树。** 有线框图/状态标注时先确认仍是当前契约，再映射到组件归属、状态与验证；视觉分歧回 Talk / Vision / Spec。见 [ui-spec](ui-spec.md)。

**动态边界也属于布局。** hover、focus、展开、浮层或悬挂命中区不能只按静态画面设计；必须说明它相对宿主、相邻内容与裁切容器的边界，避免动作层遮挡正文、与前后元素相撞，或靠负 margin 把可点击区域挤进不属于它的内容。相关状态会改变空间关系时，UI 规格须画出该状态并把无重叠/无遮挡写入验证。

**按风险选质量目标。** 继承 spec 约束，用九特征补会改变设计/验收的目标。受管理写入 issue；无常规 issue 时（后续快改）在对话结果中保留必要边界与证据计划。见 [quality](quality.md)。

**测试设计并入实现设计。** 策略复杂、用户要求 TDD 或团队要求时，在设计阶段写清；不另造测试技能文档。

**渐进式设计。** 复杂时可先交一段可验证判断；未读懂的部分不写成确定结论。

**高风险先通再铺。** 鉴权、落库、外部 API、迁移、主路径状态机等会卡死交付时，设计里标出风险顺序；动手验证走 [do](do.md) 的**穿刺**手法，不是另开管理模式。Explore 解释现状；穿刺证明**这次需求的未来通路**可通。

## 行动指南

### 锁定目标与管理方式

必须有明确目标，不强制有 issue。目标模糊 → Talk。范围/风险已需受管理 → 说明理由建议建 issue，由用户决定（管理强度见 `SKILL.md`）。

### 开工协议与现状

项目存在 `codestable/` 时，**写实现设计前**完成 `SKILL.md` 开工协议（主题检索 + 权重深读）。写前再确认：目标 issue（若有）当前版本；将引用或回写的 `codestable` 文件；相关代码局部。已掌握且无变化迹象的段落不机械重读。检索中发现的既有取舍、有界简化、坑点与失败尝试，必须进入后续设计判断（采纳、显式排除或标为待确认）。

沿最相关触发走到可观察结果，并用 `codestable/` 命中项校准“为何如此”。有 issue 且已有可靠 `## 现状如何工作` 则复用并校准；无 issue 时在对话中给紧凑模型。

有具体变化时写影响三层：必须修改 / 需要验证 / 仍待调查。不够则升级 Explore issue。

若根因命中上述状态边界信号，在方案前做一次**有界根因外推**：

1. 写清共享状态由谁拥有；列出读写它的用户动作、后台任务、回调与关闭路径。
2. 逐一检查这些入口是否会在锁内调用外部/可回入代码，或在锁外准备后无条件写回旧状态。
3. 给出判断：已证明是局部缺陷，或需要重切共享责任；后者把状态转换、快照/准备/条件提交或等价协议写入实现设计。
4. 把验证落在这条规则上，例如重入不阻塞、相邻转换不会双启动/写错绑定，而不只重跑原始症状。

用户只要求诊断时，报告外推结论和建议，不擅自扩大为架构改造；用户授权修复或已有受管理事项时，按结论调整 Design 范围。

### 质量目标与实现判断

读 [quality](quality.md)：从 **project / epic spec 继承**约束 → 按影响与失败代价补候选 → 受管理写入 issue，无 issue 时在结果中说明必要目标。未选项不写“不适用”。

基于现状与 `codestable/` 既有取舍做功能分工、数据/状态/错误路径与验证面判断。涉及 UI 时确认图标记（当前/目标/示意）未混用。用 [economy](economy.md) 梯子检查；有界简化须写上限、触发、方向。逐项响应已选质量目标。

有 hover / focus / 展开 / 浮层等动态 UI 时，补一段边界判断：它的可见面与命中区各归谁所有、相对正文和相邻元素怎样停靠、容器是否裁切，以及怎样验证静态与动态态都没有重叠、遮挡或布局跳动。

做方案前，对本次会触及的局部做一次腐化判断：列出它是“本次变化引起的归属失配”还是“既有积累的结构腐化”，以及相应处理——本次先清理、保留并开后续事项，或已证明不影响本次。不要把“文件已经很乱”当成一句背景描述后继续往里加代码。

验证策略：测可观察行为；mock 仅不可控外部依赖。接口或命令未清时标待确认，不假造测试。

跨多模块/多路径/多关键取舍时，先交第一段可验证设计，用户确认后再继续。

多处「不确定是否可行」时：在设计中列出 2–5 个风险点与「怎样算打通」，建议实现阶段先走 [do](do.md) 的穿刺手法再加厚；不要在 Design 里假装写代码。

## 产物契约

**有目标 issue（受管理）**：按认知顺序写回 `## 现状如何工作`、`## 影响范围`、`## 质量目标`、`## 实现设计`；有风险打通计划时加 `## 风险与穿刺`（表与顺序即可，结果在 Do 回写）。同职责章节更新，不另开第二份。模板：`templates/entities/issue.md`。

**无 issue（后续多走快改）**：仅对话交付；不创建 `codestable` 文件。用户随后要实现 → [fast](fast.md) 或 [do](do.md) 复用当前上下文。

`## 质量目标`：只列已选目标（特性/子特性、具体结果、来源、预期证据）；无则删除整节。

`## 实现设计` 推荐结构：这次要怎么做 → 功能怎么分工（含归属是否仍对、是否先重切）→ 请求/数据怎么走 → 哪些边界不碰 → 有界简化（如有）→ 质量目标如何落实 → 一步步怎么改（结构步在前、行为步在后，若需要）→ 怎么确认做对。若做过根因外推，明确状态所有权、转换协议、相邻入口审计结论及对应验证，不另造空泛的“架构风险”章节。
写回后检查目标、范围、质量目标、设计、验证能否互相咬合。issue 过大或边界错 → 停，建议回 Talk 澄清。

## 收尾汇报

先讲现状与影响，再讲整体实现安排（分工与数据流），再讲顺序、质量响应、风险与验证（含是否建议先穿刺）。文件路径作索引放后。

## 应用场景

- 简单明确改变先设计 → 对话交付，实现时默认 [fast](fast.md)
- 指定 issue 设计 → 写回 issue
- 有目标但还不能开写 → 补分工、流、边界、验证与顺序
- 改前需顺逻辑 → 先现状说明；不够则 Explore issue
- 高风险不确定 → 设计里标风险顺序，实现走 Do 穿刺

不适用：模糊想法 → Talk；写代码加厚 / 动手打通风险 → [do](do.md)；全仓架构审计。
