# 资料工作区应用边界收口

## 目标

在不改变资料上传、重复资料身份保持、知识库构建、OpenAPI 与前端行为的前提下，把资料上传和知识库构建从 FastAPI handler 下沉到可独立调用和测试的正式应用服务；资料归属规则只有一个所有者，HTTP 只处理协议转换与错误映射。

## 范围

- 包含：
  - 收拢 `source_type`、教材授权、默认知识库、`source_role`、`authority_tier` 的资料归属规则。
  - 建立资料工作区应用服务，拥有上传、对象存储补偿、考试身份合并、知识版本构建和失败回写流程。
  - `app/api/workspaces.py` 的资料上传与知识库构建 handler 改为调用正式应用服务。
  - 测试从 monkeypatch API 内部构造器迁移到应用服务接口；补充相对导入和本切片边界门禁。
- 不包含：
  - 改变 HTTP 路径、表单字段、响应 JSON、状态码、OpenAPI 或前端页面。
  - 改变资料类型集合、配卷解析、对象键、知识版本发布、向量参数或模型配置。
  - 本次不迁移 graph、RAG、paper submission、grading 的应用边界，也不重排 ORM model 文件。

## 归属

- 独立 issue；作为全仓结构评审后的第一条可关闭垂直切片。
- 相关 spec：`codestable/spec/index.md`
- 前置结构事项：`codestable/issues/010-x-后端领域模块化与组合根收口.md`

## 当前问题

- `backend/src/examtwin/app/api/workspaces.py` 的上传 handler 同时承担资料规则、checksum、重复身份合并、对象存储写入与补偿、PDF 页数、Repository 注册；知识库构建 handler 同时承担版本、转换、索引和失败回写。
- 教材授权、assessment-only、核心/补充知识库来源限制在 API 与 `WorkspaceRepository.assign_document()` 重复实现，`authority_tier` 只存在于 API。
- `backend/tests/test_workspace_uploads.py` 必须直接调用 handler，并替换 `_workspaces`、`corpus_repository`、`build_object_store` 三个模块全局构造器。
- 现有架构检查可以通过上述结构，也没有解析 `ImportFrom.level`，相对导入可绕过顶层依赖规则。

## 行为保持

- 必须保持的外部行为：
  - `POST /api/v1/subject-workspaces/{workspace_id}/documents` 的请求、响应、状态码、对象键、重复资料 identity 合并和失败补偿不变。
  - `POST /api/v1/knowledge-bases/{knowledge_base_id}/build` 的版本创建、转换、索引、发布和失败状态不变。
  - 教材授权、核心/补充知识库和 assessment-only 规则不变。
- 兼容性边界：数据库 schema、Alembic、对象存储键、OpenAPI 与前端生成类型不变；仓库内调用方干净迁移，不留旧 helper 或兼容 shim。
- 不借重构顺手改变的行为：不新增资料类型，不调整上传大小、并发、检索、模型、UI 或部署拓扑。

## 现状如何工作

上传请求进入 `app/api/workspaces.py` 后，handler 直接读取工作区、判定归属、计算 checksum、写对象存储、注册 Corpus 记录，再调用 Workspace Repository 二次校验与写入。知识库构建同样由 handler 直接拼装 ingestor、repository 和索引函数。失败在 handler 内回滚对象或写失败版本。

目标调用路径：

```text
FastAPI handler
  -> CorpusWorkspaceService
       -> DocumentAssignmentPolicy
       -> Workspace/Corpus repositories
       -> ObjectStore / CorpusIngestor / vector index
  -> response / HTTP error mapping
```

## 实现设计

### 这次要怎么做

- 在 `subjects` 内建立纯资料归属决策，返回最终 `knowledge_base_id`、`source_role` 和 `authority_tier`。
- 在 `knowledge` 内建立 `CorpusWorkspaceService`，注入现有 Repository、ObjectStore、Ingestor 和索引依赖。
- 上传方法接收普通 stream/元数据，不依赖 FastAPI 类型；构建方法接收 knowledge base id。
- 组合根构造服务，FastAPI dependency 提供服务；handler 只做表单和响应适配。
- 删除不再使用的 API helper 与重复 `WorkspaceRepository.assign_document()`。

### 功能 / 责任怎么分工

- `subjects`：工作区、知识库归属与资料分类规则。
- `knowledge`：资料注册、对象存储、转换和知识版本构建用例。
- `app`：依赖装配、HTTP 输入输出和异常映射。
- Repository：事务读写，不重新计算已决策的业务分类。

### 请求 / 数据 / 调用怎么走

handler 将文件流和表单交给服务；服务先解析工作区与归属，再计算内容身份并写对象；注册失败时删除本次新对象。构建时服务创建版本、转换资料、构建索引；异常时标记版本失败并向 handler 返回领域异常。

### 哪些边界不碰

不改数据模型、迁移、API 契约、对象键、模型调用、并发参数和前端。

### 质量目标如何落实

正式服务接口替代 handler 私有接缝；纯策略消除规则复制；依赖注入保留测试替身；原有补偿逻辑随用例迁移并由故障测试夹住；架构脚本保护已迁移切片。

### 一步步怎么改

1. 增加资料归属决策及边界测试。
2. 增加 `CorpusWorkspaceService` 并迁移上传和构建流程。
3. 组合根与 FastAPI dependency 接线，路由改为调用服务。
4. 迁移现有 workspace upload 测试，删除旧 helper 和重复 Repository 方法。
5. 修复架构检查的相对导入解析，并保护本切片不回退。
6. 运行专项测试、架构检查、OpenAPI 和前端类型检查。
