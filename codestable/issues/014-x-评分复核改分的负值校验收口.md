# 评分复核改分的负值校验收口

## 目标

人工复核改分时，最终分数必须落在 `[0, total_available]` 内。修复后无论从 HTTP 还是从
服务/CLI 直接调用，负值改分都被拒绝，形成单一校验点。

## 范围

- 包含：`AssessmentRepository.review` 对 `override_mark` 的负值校验；前端已有校验的对齐。
- 不包含：改变“改分须写入审计记录、确认后不可在当前界面撤销”的既有行为。

## 归属

- 独立 issue（不隶属现有 epic）。
- 相关 spec：`codestable/spec/index.md` “从已完成作答到教师复核”与“人工复核”能力边界。

## 当前证据

- 预期行为：`override_mark` 必须为 `0 <= override_mark <= total_available`。
- 实际行为：`AssessmentRepository.review`（`assessment_repository.py:119-125`）只校验
  `override_mark is None` 与 `final_mark > total_available`，**没有校验负值**。HTTP 层
  `ReviewRequest.override_mark`（`contracts/grading.py:86`）有 `ge=0`，会拦掉 API 进来的
  负值；但 `review` 方法本身若被 worker / CLI 直接调用可传入负分。
- 最小场景：直接调用 `AssessmentRepository.review(...)` 传 `override_mark=-1`，最终分被
  记为负。
- 原始证据：`backend/src/examtwin/assessment/assessment_repository.py` 的 `review`。

## 根因定位

- 最可能根因：负值校验只存在于 HTTP 契约层（Pydantic `ge=0`），服务层未下沉；域方法
  未做同一约束。
- 影响面：评分最终分正确性；功能正确性质量约束。

## 方案判断

- 在 `AssessmentRepository.review` 增加 `override_mark < 0` 时抛 `ValueError`，与
  `override_mark > total_available` 的同级校验并列。
- 补充负值改分的单元测试（覆盖域方法直接调用路径）。

## 执行记录

- 2026-08-07：在 `AssessmentRepository.review` 计算 `final_mark` 后、写入 `ReviewModel` 和
  `AssessmentModel` 前增加非负校验。校验位于仓储事务内，HTTP、服务和直接仓储调用共享
  同一约束；上界校验、审计记录和复核状态转换保持不变。
- 新增仓储直接调用测试：使用事务替身验证 `-1` 在任何写入前被拒绝，并验证 `0` 与
  `total_available` 两个边界值可以完成复核和审计记录构造。

## 验证

- 修复前用仓储直接调用最小场景复现：`override_mark=-1` 返回
  `final_mark=-1.0`、状态 `overridden`。
- 修复后评分非集成定向测试：`5 passed, 1 deselected`；其中负值拒绝、零分和满分边界均通过。
- PostgreSQL 既有评分复核集成测试：`1 passed`。
- 后端完整非集成测试：`260 passed, 23 deselected`；Ruff check、format check、
  basedpyright 全部通过。唯一 warning 为本地 Qdrant payload index 的既有提示。

## 关闭回写

- project spec：`codestable/spec/index.md` “人工复核”能力边界，确认单项/总分始终落在
  合法范围（含非负）由域方法强制。

## 关闭结论

- 目标达成：负值改分在仓储事务内、任何持久化之前被拒绝；`0` 与满分边界继续合法，上界、
  审计记录和状态转换行为未改变。
- 质量证据：负值最小场景修复前可复现；修复后仓储直接调用、PostgreSQL 集成和后端完整
  非集成回归均通过，静态检查与格式检查通过。
- 稳定约束已毕业到 `codestable/spec/index.md`“从已完成作答到教师复核”：最终人工改分必须
  位于 `[0, total_available]`，并由领域校验强制。
- 无遗留事项。
