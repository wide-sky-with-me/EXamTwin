# 评分批量与 AI 审核及整卷总览

## 目标

在现有“严格配对 Mark Scheme → 人工确认评分原子 → 逐题自动初评 → 人工复核”安全边界内，为答案评分工作台增加可审计的批量人工审核和 AI 辅助审核；逐题评分完成后提供整卷总览、总体建议和逐题建议。AI 只生成可追溯建议，不替代人工确认，不把建议分直接变成最终成绩。

## 范围

- 包含：
  - 对评分原子进行多选、批量接受、批量拒绝和混合批量决策，每条原子仍写独立审计记录。
  - 对选中或当前待审核评分原子执行 AI 审核，保存接受 / 拒绝 / 需修改建议、置信度、理由和建议修改。
  - 教师明确确认后批量应用 AI 的接受 / 拒绝建议；“需修改”仍进入单条编辑，不自动改变人工审核状态。
  - 为已确认评分规则生成整卷评分总览，显示完成度、总分、得分率、人工复核状态、共性问题、总体建议和逐题建议。
  - 拆分当前超大评分页面，使批量选择、AI 状态和总览拥有清楚的组件与状态边界。
  - 更新数据库迁移、OpenAPI、生成类型、后端/前端行为测试和架构证据。
- 不包含：
  - AI 自动确认评分规则、绕过人工复核或发布正式成绩。
  - 批量确认/改分 assessment 复核队列；本次批量能力只属于评分原子审核。
  - 批量生成所有题目的自动评分、学生账号、班级统计、跨试卷比较或长期学情画像。
  - 修改 Mark Scheme 严格配对、评分模型、现有单题评分算法和最终分合法范围。

## 归属

- 独立 issue；用户明确授权“先设计，设计完成后多 Agent 实施并反复复审”。
- 相关 spec：`codestable/spec/index.md`“从已完成作答到教师复核”“自动初评”“人工复核”。
- 相关历史：`014-x-评分复核改分的负值校验收口.md`。

## 现状如何工作

评分工作台分三步：选择既有答卷与严格配对 Mark Scheme；逐条接受、拒绝或编辑模型抽取的评分原子；确认全部原子后逐题生成建议分。单条评分原子审核由 `RubricRepository.review_criterion()` 在事务内锁定规则与原子，并追加 `RubricCriterionReviewModel` 审计记录；确认要求无 pending 且至少一个 accepted。自动初评把逐原子得分、错误类型和改进建议持久化到 assessment，页面只展示当前选中题目的最新结果。当前没有批量审核、独立 AI 审核记录或整卷聚合读模型。

现有 `Grading.tsx` 同时拥有材料加载、评分规则审核、逐题评分和全部视图渲染，已超过一千行；继续内联批量选择、AI 建议和整卷总览会形成新的状态耦合与重复派生，因此本次变化要求先按业务阶段拆出深组件，而不是继续堆条件分支。

## 行为保持

- 所有有效评分原子最终仍须有人工 reviewer、时间和接受/拒绝审计；AI 记录不计入人工审核完成度。
- 批量人工审核是单事务、全有或全无；任一 ID 越界、规则非 draft、请求重复或 patch 非法时不写部分结果。
- AI 输出与人工状态分离并追加保存；模型失败、输出缺项、ID 越界或结构不合法时不改变评分原子。
- 评分规则确认门禁不变；只有人工审核完成且至少一条接受时才能确认。
- 整卷总览只使用指定评分规则下每题最新 assessment；人工 override 后使用持久化最终分，历史重跑不重复计分。
- 总览未完成时明确显示缺少的题目，不把部分结果表述为最终整卷结论。

## 影响范围

- 必须修改：评分 contracts/API、`RubricService`、`RubricRepository`、AI 审核持久化模型与 Alembic、组合根、OpenAPI；评分页与其组件、CSS、生成类型和测试。
- 需要验证：批量事务与逐条审计、AI 与人工状态隔离、AI 重试/结构门禁、规则确认门禁、最新 assessment 聚合、人工改分后的总览、筛选/选择状态、键盘与窄屏布局。
- 不改：现有 grading provider、Question Paper / Mark Scheme 配对、单题评分结果 schema、assessment review 领域转换、RAG/知识图谱和其他页面。

## 质量目标

- 功能适合性 / 正确性：批量操作、AI 建议、整卷分数和建议均对应同一 subject、paper、rubric 版本；来源与题号不串线。证据为领域/服务/API 行为测试。
- 可靠性 / 原子性：批量人工审核全有或全无；AI 外部调用完成且全部结构校验后才一次写入；失败不改变人工状态。证据为失败与回滚测试。
- 信息安全性 / 人工控制：AI 建议不能直接确认规则或最终成绩；应用 AI 建议必须有明确 reviewer 和一次确认动作。证据为服务门禁与真实 UI 交互。
- 可维护性 / 模块化：批量规则属于 rubric 领域仓储，AI 编排与总览属于 `RubricService`，HTTP 只做协议映射；前端按审核阶段和总览阶段拆分，不在 `Grading.tsx` 继续堆积。
- 可测试性：模型通过现有 `StructuredModelPort` 注入；测试 mock 仅替代模型，不替代事务、聚合和 HTTP 可观察行为。
- 可访问性 / 易用性：批量选择有可见计数、全选仅作用于当前筛选结果、危险批量拒绝和应用 AI 建议须确认；sticky 工具栏不遮挡正文，键盘 focus、窄屏换行和 reduced motion 保持可用。
- 性能效率：AI 按题目分组并有界并发，不按原子逐次请求；整卷总览复用已加载 assessment，不产生前端请求瀑布或每题 N+1 查询。

## 实现设计

### 这次要怎么做

建立三条相互独立但共享 rubric 版本的能力：批量人工决策、AI 审核建议、整卷评分读模型。批量决策扩展现有单条审核事务，不复制审核规则；AI 建议使用单独的追加式记录，不修改人工字段；总览从已持久化的最新逐题结果确定性聚合，不增加另一个会漂移的“总分事实源”。

### 后端分工

- `contracts/rubrics.py`：增加批量决策、AI 审核请求/响应、AI 建议和整卷总览契约；criterion response 暴露最新 AI 建议。
- `RubricRepository`：
  - `review_criteria_batch` 锁定 rubric 与全部目标原子，验证完整集合后逐条写人工审计并一次提交；单条审核复用同一内部转换。
  - `record_ai_reviews` 只追加 AI 记录；`get` 为每条原子投影最新记录。
- `RubricService`：
  - `ai_review_criteria` 验证 subject/rubric/draft/目标原子，按题号分组，用题目正文、Mark Scheme 上下文和当前原子执行有界并发结构化审核；全部结果 ID 闭合后统一持久化。
  - `grading_overview` 选择指定 rubric 下每个 question position 最新 assessment，结合 accepted criteria 的可用分，生成完成度、得分率、错误类型频次、强项/待改进题和去重后的总体/逐题建议。
- API：增加批量审核、AI 审核和整卷总览三个 endpoint；沿用 404/409/422/502 错误语义。
- 数据库：增加 `rubric_criterion_ai_reviews` 追加表，保存 recommendation、confidence、rationale、suggested_updates、model、created_at；不在 criterion 上混入 AI 状态，不增加总览表。
- Prompt：新增版本化 rubric-review prompt；模型输出严格 Pydantic，recommendation 仅允许 `accept | reject | revise`，建议 patch 仍须通过现有字段校验和人工动作。

### 请求与状态怎么走

1. 教师勾选当前筛选下的评分原子。
2. 批量接受/拒绝：前端提交每条 decision；Repository 在一个事务中验证并追加每条人工审计。
3. AI 审核：Service 对选中 pending 原子按题分组审核；全部模型结果闭合后追加 AI 记录，人工 `review_status` 保持 pending。
4. 应用 AI 建议：前端显示将接受/拒绝/保留待修改的数量；教师填写 reviewer 并确认后，使用通用批量决策 endpoint。`revise` 项不自动处理。
5. 评分阶段每次生成结果后刷新 assessments 与 overview；全部可评分题均有结果时进入“整卷总览”。
6. 总览按最新结果展示总分和逐题诊断；未完成或存在失败题时显示缺口，不伪造最终建议。

### 前端信息架构与视觉设计

评分旅程扩展为四步：准备材料 → 审核得分点 → 逐题评分 → 整卷总览。保持现有冷静的工作台视觉，不另造营销式仪表盘。

步骤 2 使用“审核台”布局：上方筛选，紧邻内容的是不遮挡正文的 sticky 批量工具条；每条原子左侧复选框，右侧 AI 建议以证据批注形式嵌入卡片。批量拒绝和应用 AI 建议使用明确确认面，不做一键静默接受。

```text
[审核人] [题号] [状态]                     8 / 24 已选择
[选择当前待审核] [AI 审核] [批量接受] [批量拒绝] [应用 AI 建议]
────────────────────────────────────────────────────────────
☑ Q1 · M1 · 1 分       待审核     AI: 建议接受  92%
  得分点描述……                        理由与 Mark Scheme 摘录
```

步骤 4 的记忆点是“逐题诊断轨”，而不是通用大数字卡片：顶部一条整卷得分/完成度基线，下面按试卷顺序排列每题得分段、复核状态、主要问题和可执行建议；颜色只编码状态，文本和图标同时表达含义。

```text
整卷 42 / 60 · 12 / 12 已评分 · 3 / 12 已人工复核
总体建议：先修正图像解释与单位书写，再提高长题论证闭合度。
Q1  ████████  4/5   概念准确       建议：补充单位
Q2  ████░░░░  3/8   论证不完整     建议：先定义再评价
Q3  ─────────  未评分              先完成本题评分
```

组件归属：`Grading.tsx` 保留跨阶段加载与命令编排；抽出 `RubricReviewStage`、`RubricCriterionEditor`、`GradingQuestionStage`、`GradingOverview`。长列表使用稳定 key 和派生 Map/Set；独立请求并行，避免 effect 链式瀑布。

### 边界与动态状态

- 工具栏 sticky 在审核面板内部，占据正常布局高度；窄屏改为两行，不覆盖第一张卡片。
- 选择集合在 rubric、题号筛选或版本切换时清理不存在 ID；“全选”只选择当前可见且可审核项。
- AI 运行时保留当前选择并禁用冲突操作；失败显示可重试状态，不清掉既有 AI 建议。
- 总览加载、部分完成、全部完成、无可评分题、重跑产生新 assessment 五种状态均有明确文案。

### 有界简化

- 总体建议由最新逐题改进建议、错误类型和得分比例确定性聚合，不新增第二次 LLM 总结调用和总览持久化表。上限：只做单试卷、单 rubric 版本、最新 assessment。若未来需要教师编辑总评、跨次比较或正式报告发布，再升级为版本化 report 实体。
- AI 审核同步执行并按题有界并发，不先引入后台任务状态机。触发升级：真实 rubric 规模或供应商延迟超过现有 HTTP timeout 边界，届时复用持久任务模式。

### 实现顺序

1. 穿刺批量仓储事务与 AI 建议表/迁移，证明人工状态隔离和审计闭合。
2. 增加 contracts、Repository、Service 和 API；补领域、失败和 HTTP 测试。
3. 生成 OpenAPI 类型；拆分评分页阶段组件。
4. 实现批量选择、AI 建议/应用确认和整卷诊断轨。
5. 运行后端专项、前端 Vitest/ESLint/TypeScript、OpenAPI；浏览器走完整流程并检查窄屏与键盘。
6. 多 Agent 从行为、架构、安全、测试和 UI 五个角度复审；修复后重复验证直至无 P0/P1/P2 且 UI 验收通过。

### 怎么确认做对

- 20 条中任一非法批量 decision 使 20 条全部不变；成功时产生 20 条独立人工审计。
- AI 审核后 criteria 仍为 pending，确认 rubric 仍被拒绝；教师应用建议后才改变人工状态。
- AI 结果缺 ID、多 ID、越界 ID、非法 patch 或模型失败均不写部分记录。
- 总览只计每题最新且属于当前 rubric 的 assessment；override 后总分更新，旧重跑不重复累计。
- 部分完成明确显示未评分题；全部完成显示总分、总体建议和每题建议。
- 前端批量操作作用于可见选择，确认与错误态清楚；sticky 工具栏无覆盖，键盘和窄屏可用。
- OpenAPI 与生成类型一致，现有单条审核、规则确认、逐题评分和人工复核行为继续通过。

## 风险与穿刺

| 顺序 | 风险 | 怎样算打通 |
|---|---|---|
| 1 | 批量事务部分提交或审计遗漏 | 注入中间非法项后零写入；成功数量与审计数量完全一致 |
| 2 | AI 建议误当人工决定 | AI-only 后 confirm 必须失败，criterion 人工字段保持不变 |
| 3 | AI 结果与题号/原子串线 | 输入输出 ID 集合严格相等，按 subject/rubric/question 三层闭合 |
| 4 | 总览重复统计历史 assessment | 同题两次评分只取指定 rubric 最新记录，override 使用最终持久分 |
| 5 | 超大页面继续腐化 | Grading 页面只保留编排，阶段 UI 与派生状态进入独立组件并有行为测试 |
