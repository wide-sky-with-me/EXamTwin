# 课程扩展主流程去硬编码

## 目标

把当前“声明式 SubjectPack + 主流程内置数学/经济行为”收口为受控课程运行契约：通用资料、知识、作答和验证流程只依赖显式 SubjectContext 与宿主注册能力，不判断具体科目代码；普通新增科目只增加 Subject Package，新增专用能力只增加受审查 provider，不修改主流程。

## 范围

- 包含：移除领域与仓储中的 9660 静默默认；移除作答主流程的 9660 分支；把视觉/制品要求下沉到课程运行策略；把工具装配改为宿主能力注册；区分可扩展 capability ID 与稳定制品形状；把 Board、normalizer、visual policy 的解析从 package loader 内置字典抽离；增加合成第三科和架构门禁。
- 不包含：执行任意课程包代码；新增第三个真实科目；改变现有数学/经济答案内容；重做现有 UI；实现 Examiner Report 难度证据。

## 归属

- 隶属 Epic：`codestable/epics/001-o-多科目知识生产与难度证据流水线/spec.md`
- 来源 Vision：`codestable/vision/index.md`
- 相关 Project Spec：`codestable/spec/index.md`

## 当前问题

- `assessment/paper_jobs.py` 与 `assessment/answering_agent/verification.py` 直接判断 `subject_code == "9660"`。
- `assessment/answering_agent/factory.py` 固定导入并创建数学、概率和经济工具。
- `contracts/evidence.py` 把课程能力名称固化为数学/经济 Literal，前端也固定解释这些名称。
- `knowledge/corpus_repository.py`、`knowledge/ingestion.py`、`knowledge/inventory.py`、`knowledge/publication.py` 在缺少上下文时静默回退 9660。
- `subjects/packages.py` 内置 Board、normalizer 和 visual policy 字典；`knowledge/inventory.py` 在通用分类中出现课程名。
- 当前 Package 自动发现、SubjectContext、科目隔离和 Skill 选择已经形成正确骨架，应保留并加深，而不是重写。

## 行为保持

- 数学 9660 与经济 9640 的资料、检索、整卷作答、图形产物、评分和复核行为保持不变。
- 现有 Subject Package manifest 与已持久任务可继续读取；不重建现有知识版本或向量索引。
- 正则仍可用于稳定词法格式、安全校验和 SubjectPack 内受控 Unit 解析；不得承担学科语义决策。
- 课程包保持声明式，不能从目录加载任意 Python 代码。

## 现状如何工作

工作区解析 SubjectContext 后，大部分服务已按科目隔离；Answering Runtime 也会选择当前包的 Skill。但工具实现、视觉验证、部分来源识别和兼容默认仍由通用模块直接认识数学/经济，导致新增科目需要修改主流程和共享契约。

## 影响范围

- 必须修改：SubjectRuntime/能力策略、回答工具装配、作答制品验证、公共证据契约、语料入口显式上下文、Package provider registries、架构检查与相关测试。
- 需要验证：历史答案反序列化、OpenAPI/前端类型、数学原图叠加、经济图、CLI 兼容入口、现有 Subject Package digest。
- 仍待调查：当前封闭 tool Literal 的历史数据取值范围；所有兼容函数是否仍有生产调用方；新增 provider registry 的最小公开面。

## 质量目标

- 可维护性：通用模块不包含已知科目代码或课程语义分支；合成未知科目通过同一装配路径。
- 灵活性：已有通用能力的新科目只需添加 manifest/SKILL；新增专用能力只注册 provider，不修改任务、Worker 与验证主流程。
- 可靠性：缺 SubjectContext 立即失败，不产生跨科静默写入；历史数学/经济行为回归通过。
- 信息安全性：课程包只能引用宿主白名单 capability/provider ID，不能导入或执行任意代码。
- 兼容性：既有持久答案、OpenAPI 和前端显示可迁移且不丢失。

## 方案判断

采用“声明式 Subject Package + 宿主受控 Provider Registry”，而不采用任意可执行插件。主流程依赖一个窄 SubjectRuntime：课程结构、来源身份策略、能力集合和答案制品策略。能力 ID 可扩展并在运行时校验；持久化与前端只依赖少量稳定制品形状。

## 风险与穿刺

- 风险 1：开放 capability ID 后削弱结构校验。先用受控 ID 类型与 registry 校验替代封闭学科 Literal。
- 风险 2：数学原图叠加策略分散。先把两个现有 9660 分支合并为 package artifact policy，并证明同一数学回归通过。
- 风险 3：移除 9660 默认导致旧 CLI/测试失败。先识别显式兼容外壳，领域与 Repository 严格失败，兼容入口负责注入默认。
- 风险 4：工具 registry 重构影响 Agent。先保持工具实例与名称不变，只改变装配所有权，再运行 Agent/整卷回归。

## 实现设计

### 这次要怎么做

先建立受控 provider/capability registry 和课程制品策略，再把主流程中的科目判断与工具固定装配迁到该边界；随后移除隐式数学默认，最后收紧公共契约并增加第三科门禁。

### 功能 / 责任怎么分工

- `subjects`：拥有 SubjectRuntime、Board/normalizer/artifact policy provider 注册与 Package 引用解析。
- `assessment`：只消费当前 SubjectRuntime 给出的能力和验证要求。
- `knowledge`：所有入口要求显式 SubjectContext/SubjectPack，BoardPolicy 负责来源身份规则。
- `contracts`：保存稳定通用制品结构，不枚举课程名称。
- `app`：组合根创建宿主 provider registry；兼容 CLI 在边界注入明确默认。

### 一步步怎么改

1. 写合成第三科与“通用模块禁止科目代码”的失败测试。
2. 抽出 artifact policy，迁移 9660 原图叠加判断。
3. 抽出 capability provider registry，迁移工具装配并保持现有名称。
4. 将课程专用工具名称从稳定制品形状中分离，补历史兼容解析和前端通用展示。
5. 移除 Repository/Ingestion/Inventory/Publication 的 9660 隐式默认。
6. 抽出 Board/normalizer/visual providers；package loader 只解析和查 ID。
7. 扩展架构检查并跑完整门禁、双科真实冒烟。

### 怎么确认做对

- 合成 SubjectPack `9999` 可建 SubjectContext、装配通用 knowledge_search 并通过作答运行时构建。
- `knowledge/`、`assessment/`、`app/`、`platform/` 不出现 `9640`/`9660` 业务字面量。
- 缺科目上下文的写入测试明确失败。
- 数学 plot/overlay、经济 diagram、普通文本答案回归一致。
- 新 provider 使用注册 ID 即可被课程包引用，主 factory 不导入课程实现。
