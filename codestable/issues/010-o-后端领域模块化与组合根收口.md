# 后端领域模块化与组合根收口

## 目标

在不改变 HTTP、OpenAPI、CLI/Worker、数据库与对象存储外部行为的前提下，把后端从 `api / schemas / services / persistence / composition` 横向分层迁移为按业务能力聚合的模块；每个模块拥有自己的应用服务、端口、适配器和公开入口，应用组合集中在唯一启动边界，删除旧路径与重复归属。

## 范围

- 包含：
  - `subjects`：科目目录、Subject Package、运行上下文与能力声明。
  - `knowledge`：corpus、ingestion、curriculum、difficulty、graph、retrieval、knowledge-base publication。
  - `assessment`：papers、answering、grading、rubric、review、answer evidence、task events、agent run ledger。
  - `platform`：database/session/migrations、object store、vector client、LLM/provider、agent runtime、observability/request context。
  - `app`：FastAPI 应用、router 注册、lifespan、CLI/Worker 入口与组合根。
  - 现有调用方、测试、导入路径和制度文档的完整迁移；删除迁移后不再使用的横向目录与 `composition.py`。
- 不包含：
  - 新业务功能、接口字段、状态机或页面行为。
  - 数据库 schema、Subject Package 内容、模型提示词、检索/评分算法调整。
  - 引入消息总线、DI 框架、Celery/Kafka/Redis，或新建通用 `common`、`utils`、`base_service` 抽象层。

## 归属

- 独立 issue。
- 相关 spec：`codestable/spec/index.md`

## 当前问题

- 当前后端约 139 个 Python 源文件、11,355 行；核心业务分散在 `api/`、`schemas/`、`services/`、`persistence/`、`composition.py`，一个功能变化通常横跨多个目录，责任归属只能靠文件名和人工记忆判断。
- `api/` 同时承担 HTTP 适配、业务编排和持久化组装；例如 `api/graphs.py`、`api/workspaces.py` 直接创建 SQLAlchemy Session 与 Repository，绕过稳定的应用服务边界。
- `services/` 同时包含 corpus、curriculum、graph、retrieval、paper worker、grading、storage 等不同生命周期的能力；`persistence/` 也按技术类型集中，业务边界无法从目录结构看出。
- 根级 `composition.py` 汇集大量 provider、repository、service 与 worker 构造，成为全局依赖热点；功能内部也存在反向依赖，例如 answering agent 直接导入根级 `services`。
- `subjects/`、`answering_agent/`、`agent_harness/` 已形成部分垂直边界，但与旧横向目录并存，出现同一能力多处归属、公开入口不清和旧路径难删除的问题。
- 现有模块化约束主要靠约定，没有可执行的依赖方向保护；继续增加科目、工具、Worker 或检索能力会放大横向散落和组合根耦合。

## 行为保持

- 必须保持的外部行为：
  - 所有 `/api/v1` 路由、请求/响应 JSON、HTTP 状态码、OpenAPI 文档与前端生成类型不变。
  - `examtwin` CLI、paper worker、storage GC、healthcheck 的命令、任务状态、租约/重试/恢复语义不变。
  - 科目选择、Subject Package 能力、corpus/knowledge/graph 发布、RAG、整卷作答、评分与人工复核结果不变。
  - PostgreSQL、Qdrant、对象存储中的既有数据、键、版本、alias 与迁移链保持兼容。
- 兼容性边界：Python 内部导入路径允许一次性迁移；仓库内调用方必须全部更新，不保留旧模块 re-export、别名或兼容 shim。
- 不借重构顺手改变的行为：不调整 prompt、模型、并发度、超时、重试、检索参数、评分规则、UI 或部署拓扑。

## 现状如何工作

一次 HTTP、CLI 或 Worker 触发先进入 `api/` 或 `cli.py`，再由 `composition.py` 或路由内构造 repository/service；业务服务跨 `services/`、`persistence/`、`subjects/`、`answering_agent/` 协作，最终写 PostgreSQL/Qdrant/对象存储并返回结果。依赖方向并不稳定：入口可能直达 persistence，agent 也可能反向调用根级 service。

目标依赖方向：

```text
app/bootstrap ──► feature.http / feature.wiring / feature.public
                         │
                         ▼
                 feature.application ──► feature.domain
                         │
                         ▼
                    feature.ports ◄── feature.persistence
                                         │
                                         ▼
                                      platform

feature A ──► feature B.public      （禁止导入 B 的内部实现）
domain/application                  （禁止依赖 FastAPI、SQLAlchemy、Qdrant、boto3、LiteLLM）
platform                            （禁止反向依赖业务 feature）
```

## 影响范围

- 必须修改：`backend/src/examtwin/` 下的业务包、所有内部导入、应用/CLI/Worker 组合入口、相应后端测试；迁移完成后更新 `README.md` 与 `codestable/spec/index.md` 的当前结构说明。
- 需要验证：后端静态检查与测试、OpenAPI 生成一致性、Compose 健康检查、9640/9660 科目状态 smoke、整卷 job smoke、grading/review smoke、knowledge/graph 检索与发布 smoke。
- 仍待调查：模块迁移顺序中跨 feature 的最小公开契约；`agent_harness` 应保持独立 platform capability 还是归入 `platform/agent_runtime`；哪些 persistence model 确实共享、不能自然归属单一 feature。

## 质量目标

- 可理解性：一次业务变化的核心实现与测试集中在一个 feature 下；从目录即可判断责任和公开入口。
  - 来源：本次结构审计。
  - 预期证据：代表性变更不再同时新增根级 `api/schemas/services/persistence` 文件；旧横向目录最终删除。
- 可修改性：feature 内部实现可替换，其他 feature 只依赖明确的 `public` 契约。
  - 来源：本次结构审计。
  - 预期证据：静态依赖检查拒绝跨 feature 内部导入、domain/application 依赖框架、platform 反向依赖业务模块。
- 可测试性：HTTP、CLI、Worker 只做输入输出适配和调用 application，不直接管理数据库事务或拼装完整依赖图。
  - 来源：本次结构审计。
  - 预期证据：入口测试可替换 feature public port；Repository/事务测试留在所属 feature。
- 行为稳定性：重构前后的 API 契约、关键 smoke 结果和持久化语义一致。
  - 来源：refactor 行为保持约束。
  - 预期证据：OpenAPI check 无差异，现有测试与分阶段端到端 smoke 通过。

## 方案判断

采用渐进式、feature-first 的干净切换，不做全仓一次性重写：先固化依赖规则与行为基线，再按 `subjects → knowledge → assessment → platform/app` 逐个垂直切片迁移。每一片同时迁移入口、应用逻辑、端口、适配器、调用方与测试；旧路径在该片完成时立即删除，不建立第二套长期并存架构。

按业务归属放置 persistence adapter，而不是把所有数据库代码重新集中到 `platform/database`。`platform` 只提供连接、Session、客户端和基础设施能力；事务与查询语义仍由所属 feature 负责。

## 实现设计

### 这次要怎么做

将后端收敛为以下主结构，具体文件名沿用现有领域术语，避免再造抽象：

```text
backend/src/examtwin/
├── app/                    # bootstrap、FastAPI、CLI/Worker、全局 wiring
├── subjects/               # catalog、package、context、public、wiring
├── knowledge/              # corpus/curriculum/graph/retrieval 子能力
├── assessment/             # papers/answering/grading 子能力
├── platform/               # database、object_store、vector、llm、agent_runtime、observability
└── contracts/              # 真正跨进程/跨 feature 的稳定数据契约
```

每个 feature 仅在需要时使用 `domain.py`、`application.py`、`ports.py`、`persistence.py`、`http.py`、`public.py`、`wiring.py`；不机械创建空层或同名样板文件。

### 功能 / 责任怎么分工

- `domain/application`：业务规则、用例编排、事务边界；不导入框架与具体 provider。
- `ports`：application 所需的最小 Protocol；按消费者定义，不复制整个 Repository 接口。
- `persistence/http`：SQLAlchemy、FastAPI 等入站/出站适配器。
- `public`：其他 feature 可依赖的稳定能力与数据类型；内部模块不对外开放。
- `wiring`：仅构造本 feature；全局组合只在 `app/bootstrap.py`。
- `platform`：拥有基础设施客户端及生命周期，不拥有 corpus、graph、paper、grading 等业务规则。

### 请求 / 数据 / 调用怎么走

HTTP/CLI/Worker 将外部输入转换为 feature request，调用 `feature.public` 暴露的 application use case；application 通过 ports 使用 repository/provider；adapter 借助 platform 客户端完成 I/O；结果沿同一路径转换为现有响应或事件契约。

跨 feature 调用只允许 `feature_a.application → feature_b.public`，禁止 `feature_a → feature_b.persistence/domain/http/wiring`。

### 哪些边界不碰

- 保留 Alembic revision 历史与 SQLAlchemy model 映射，先移动归属再考虑任何 schema 变化。
- 保留现有 provider-neutral Agent Harness 运行协议；只调整宿主位置和依赖方向。
- 保留 Subject Package 的 manifest、SKILL、catalog 与 runtime 行为。
- 不把 React 前端纳入此次目录重构；仅用其 OpenAPI 类型检查证明契约未变。

### 质量目标如何落实

- 在首个切片前增加可执行的包依赖规则，明确 allowlist；每完成一片同步收紧，最终禁止旧横向层重新被导入。
- 每片迁移用现有行为测试与一个端到端 smoke 夹住，避免“先搬文件、最后统一修复”。
- 使用 LSP/AST 迁移符号和导入；迁移导出符号前检查所有引用，完成后删除旧文件和 re-export。
- 组合根只管理生命周期与依赖构造；禁止在 wiring 中重新实现业务分支。

### 一步步怎么改

1. 记录当前 OpenAPI、CLI 命令、测试与 9640/9660 smoke 基线；加入包依赖方向检查。
2. 收口 `subjects`：合并 catalog、Subject Package、runtime context 与 capability public contract，迁移所有调用方，删除旧入口。
3. 迁移 `knowledge`：按 corpus/ingestion/curriculum、graph、retrieval/publication 三个内部切片完成 API、service、repository、worker 迁移。
4. 迁移 `assessment`：先 grading/review，再 papers/answering/worker/agent tools；通过 public contract 访问 knowledge 与 subjects。
5. 收口 `platform`：移动共享基础设施客户端与生命周期，切断其对业务 feature 的反向依赖。
6. 建立 `app/bootstrap.py` 与 feature wiring，迁移 FastAPI/CLI/Worker 入口；删除根级 `composition.py`。
7. 删除已空的 `api/`、`schemas/`、`services/`、`persistence/` 旧路径、旧 re-export 与过渡 allowlist。
8. 更新 README、Project Spec 的当前结构与依赖规则，执行全量验证并关闭事项。
