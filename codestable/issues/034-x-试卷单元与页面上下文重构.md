# 试卷单元与页面上下文重构

## 目标
把目前靠 `subject_code + pair_key` 临时拼接的试卷、Mark Scheme、Insert 和作答任务，收敛为有稳定 ID、显式关联和生命周期的“试卷单元”；同时让科目、试卷、作答、评分、复核拥有可复制、可刷新、可前进后退的 URL 上下文。

## 当前问题
- `source_documents` 同时承担文件库存和试卷业务对象；页面把每份 Question Paper 当作一张“试卷”，再按 `pair_key` 临时搜索材料，无法表达显式绑定、解绑和整组删除。
- 同一严格配对键可能存在多份 Question Paper；直接按 `pair_key` 聚合会丢失来源，直接把文件升级成试卷又无法承载多个材料。
- `paper_jobs` 保存了 `pair_key` 和 Source Booklet 快照，但没有指向被管理的试卷单元或 Question Paper 文档；评分只能在作答任务与 Mark Scheme 之间临时配对。
- 前端用单个 `tab` 状态模拟页面，科目选择分散在多个页面组件中；刷新、浏览器历史、从试卷进入作答/评分都不能保持业务上下文。

## 行为保持
- 必须保持的外部行为：现有上传作答、外部答卷导入、后台解析、评分规则冻结、复核队列和旧作答记录仍可使用。
- 兼容性边界：历史作答可只有 `paper_unit_id` 而没有精确 Question Paper 文档；新建作答必须同时冻结试卷单元和 Question Paper 文档。
- 不借重构顺手改变：模型调用、分题契约、评分算法、知识库选择与对象存储留存策略。

## 现状如何工作
用户在“试卷管理”上传 Question Paper 后，系统把它注册为 `source_documents`；页面按相同 `pair_key` 查找 Mark Scheme 和 Insert，并把这种查询结果称为绑定。用户进入作答或评分后还要再次选择科目和作答任务。

## 影响范围
- 必须修改：数据库模型与 Alembic 迁移、试卷单元仓储/服务/API、作答任务来源关联、OpenAPI 客户端、应用路由和科目上下文、试卷管理/作答/评分入口。
- 需要验证：重复 Question Paper 无损迁移；严格身份与角色校验；删除约束；旧作答兼容；URL 刷新/前进后退；桌面和 390px 窄屏。
- 不包含：把历史作答文件反向去重进资料库存；改变评分或复核结果模型；批量 OCR 或重新转换全部历史文档。

## UI 变化 / 实际与预期
- 角色与入口：侧栏只负责顶级能力；科目是路由上下文，试卷单元是作答和评分的共同上文。
- 目标结构：
```text
/subjects
/subjects/:subjectId/papers
/subjects/:subjectId/papers/:paperUnitId
/subjects/:subjectId/papers/:paperUnitId/answers
/subjects/:subjectId/papers/:paperUnitId/documents/:documentId
/subjects/:subjectId/papers/:paperUnitId/jobs/:jobId/answering
/subjects/:subjectId/papers/:paperUnitId/jobs/:jobId/grading
/reviews
```
- 交互：试卷管理先展示科目索引；进入科目后按试卷单元分页搜索。每个单元展示全部 Question Paper、Mark Scheme、Insert 和关联作答；新增、重命名、绑定/解绑、归档均操作单元而不是伪装成文件操作。
- 稳定约束：同一页面只出现一个科目选择来源；页面标题和浏览器历史反映当前科目与试卷单元；危险删除明确受关联作答/评分记录保护。

## 方案判断
采用 `paper_units` + `paper_unit_documents`：
- `paper_units` 以 `(subject_id, pair_key)` 唯一标识一次考试单元，保存显示名、年份、考季、Unit 和归档状态。
- `paper_unit_documents` 显式保存单元内每份资料及其角色，允许历史重复 Question Paper 无损进入同一单元；一个来源文档只能属于一个试卷单元。
- `paper_jobs` 增加 `paper_unit_id` 与 `question_paper_document_id`。迁移按严格配对键回填单元；旧作答无法可靠判定重复 QP 时只回填单元，新作答从受管文档创建时同时冻结两者。

没有采用把三个外键直接放在 `paper_units` 上：现有数据已证明同一角色可能有多份来源，单值外键会在迁移时静默丢数据。

## 实现设计
### 功能 / 责任怎么分工
- `PaperUnitRepository`：试卷单元、文档关联、分页筛选、删除保护和作答关联查询。
- `PaperUnitService`：科目边界、严格身份、资料角色、显式绑定与受管试卷作答创建。
- `CorpusWorkspaceService`：继续只负责文件上传与资料库存，不再代表试卷业务生命周期。
- `PaperJobService`：继续负责作答任务；接受可选试卷单元和 Question Paper 文档快照并写入任务。

### 请求 / 数据 / 调用怎么走
1. 上传资料仍先进入科目资料库存并完成需要的转换。
2. 创建或更新试卷单元时，服务验证所有文档属于当前科目、状态可用、`pair_key` 完全一致且角色与 `source_type` 一致，再事务写入关联。
3. 从试卷单元发起作答时，后端从对象存储物化所选 Question Paper，冻结 `paper_unit_id`、`question_paper_document_id`、知识库快照与可选 Insert，再创建原有后台任务。
4. 评分继续针对完成的 `paper_job`，但页面通过 `paper_unit_id` 只展示当前试卷单元的任务和严格匹配的 Mark Scheme。

### 哪些边界不碰
- `pair_key` 仍由现有考试身份解析器生成，不能由向量相似度或 UI 自由输入替代。
- 文档归档不物理删除对象；已被作答、评分或难度证据引用的文档不能通过试卷单元删除绕过审计。
- 删除试卷单元采用归档；存在关联作答时拒绝归档，避免留下无上文任务。

### 一步步怎么改
1. 新增模型、迁移与迁移回归测试，先证明重复资料无损。
2. 新增仓储、服务、契约和 API；覆盖列表、创建、更新绑定、归档、从受管试卷创建作答。
3. 生成 OpenAPI 类型并迁移前端数据调用。
4. 引入声明式路由和单一科目上下文；把试卷管理改为试卷单元视图。
5. 让作答和评分接受路由中的 `subjectId/paperUnitId`，移除同页重复科目选择。
6. 运行后端领域测试、前端行为测试、构建和真实浏览器桌面/窄屏流程。

## 验证
- 迁移测试：同一 `pair_key` 的多份 QP/MS/Insert 全部关联，历史作答正确回填且歧义 QP 不伪绑定。
- API 测试：科目隔离、分页搜索、角色/配对拒绝、创建更新归档、有关联任务时删除保护、从受管文件创建作答。
- 前端测试：URL 刷新和前进后退、科目上下文不重复、试卷单元筛选分页、从单元进入作答/评分。
- 实机：1440px 与 390px 完成科目→试卷单元→作答/评分主路径，无水平溢出。

## 执行记录
- 2026-08-12：完成现状映射与目标模型设计；现库迁移后形成 113 个试卷单元、280 条显式资料关联，9 个单元保留了多份 Question Paper，没有把重复来源静默覆盖。
- 2026-08-12：新增 `paper_units` / `paper_unit_documents`、试卷单元领域服务和工作区 API；作答任务冻结 `paper_unit_id` 与具体 Question Paper 文档，评分列表可按试卷单元收窄。
- 2026-08-12：前端切换为 React Router URL 上下文；试卷管理提供分页搜索、年份/考季/Unit 筛选、创建、重命名、显式资料绑定和受保护归档，试卷详情可进入作答与评分。

## 关闭结论
- 目标已达成：试卷不再由页面临时拼接文件；科目、试卷单元、作答任务和评分入口均有可刷新、可复制、可前进后退的 URL。
- 数据边界成立：每个活动试卷单元至少关联一份活动 Question Paper；现库 113 个单元均满足该约束，试运行创建的作答任务同时保存试卷单元与 Question Paper 文档。
- 质量证据：后端 456 passed / 21 skipped，Ruff 与 basedpyright 通过；前端 16 个 Vitest 文件 / 118 项测试、ESLint、TypeScript、Vite 生产构建与 OpenAPI 类型快照检查通过。
- 实机证据：1440px 与 390px 均完成科目试卷列表、试卷详情、试卷上下文作答和评分路由；三条页面路径无水平溢出、无可见错误，浏览器后退/前进保持试卷与作答任务上下文。
